- 2026-10-13: The Node `DEP0040` punycode notice in test output comes from a transitive dependency of the deprecated pool; it should vanish when we migrate to `@cloudflare/vitest-plugin`. Scripts left unchanged.
- 2026-10-13: Better Auth 1.7.7 installed (the brief assumed 1.7.6's schema; migration 0001 still matches, sign-up/sign-in work on it).
- 2026-10-13: Better Auth 403s any cookie-carrying POST with no `Origin` header (`MISSING_OR_NULL_ORIGIN`); sign-up and sign-in carry no cookie so pass. The brief's sign-out test sent none, so the signed-out session stayed valid and `/api/cart` stayed 200. The test now sends `origin: http://shop.test` on sign-out, as a browser does.
- 2026-10-13: That Origin must match `BETTER_AUTH_URL`; the wrangler var is `http://localhost:8787`, so `vitest.config.ts` binds `BETTER_AUTH_URL: "http://shop.test"` for tests (without it sign-out is still 403 INVALID_ORIGIN).
- 2026-10-13: Planted bug confirmed on main: with `BETTER_AUTH_SECRET` undefined the Worker still signs up and answers 200 (Better Auth falls back to its public default secret); `refuses to run without BETTER_AUTH_SECRET` fails on purpose.
- 2026-10-13: Building Better Auth on every `/api/*` request made `test/errors.test.ts`'s `{ prepare }` stub fail with an unhandled rejection "BetterAuthError: Failed to initialize database adapter" (it needs a D1-shaped object). The stub now also has `batch` and `exec`, all throwing; the assertions are unchanged.
- 2026-10-13: Better Auth success bodies are not the envelope ({ token, user } or { status: true }), and src/lib/api.ts throws unless body.ok is true; the /api/auth/* handler now wraps them as { ok, data, error } with the same status and copies every header (Set-Cookie survives; c.json would drop it). Errors map by status (400, 403, 422, 429; 401 says "Wrong email or password" only on sign-in/sign-up paths, else "Not signed in"). A duplicate sign-up is 422 on 1.7.7, as assumed.

- 2026-10-13: With no `scheduled` export, `SELF.scheduled(...)` does not return a non-ok outcome; it throws `TypeError: Expected default export of worker/index.ts to define a `scheduled()` function`, so `runs from the Cron Trigger` fails by exception, and workerd logs the same text as an uncaught-exception info line.

- 2026-10-13: On `main` the cart is per-isolate memory, so checkout answers "Your cart is empty" after the planted header log runs; the log test fails twice (the token is in the logged `cookie` header, and the Stripe interceptor is never called so `assertNoPendingInterceptors` throws), both the one planted failure.
- 2026-10-13: Reading `wrangler.jsonc` with `new URL("../../wrangler.jsonc", import.meta.url)` fails `pnpm typecheck` (dom `URL` is not node's `URL`, so `readFileSync` rejects it); the test uses `resolve(import.meta.dirname, ...)` instead.
- 2026-10-14: workerd has no synchronous SubtleCrypto, so `stripe.webhooks.generateTestHeaderString` throws in the Workers pool; the webhook test signs with `generateTestHeaderStringAsync`. Until this fix, `writes the order and empties the cart` and `records the order once when delivered twice` had been failing on `main` in the signing helper (since Task 5), not for the planted reason.
- 2026-10-14: An R2 object whose body is never read aborts the Workers pool ("unable to pop R2 storage", "Isolated storage failed", exit 1); the upload test now reads the body of the object it gets. The Task 6 run never reached this because the planted route returned null, so `expect(object).not.toBeNull()` failed first.
- 2026-10-14: In pool 0.12 `SELF.scheduled(...)` resolves to `undefined` (and `SELF` is typed as a plain Fetcher), so the cron test calls the exported handler through `createScheduledController` and `waitOnExecutionContext`. It reads the handler as `ExportedHandler<Env>` so it compiles on `main`, where the Worker has no `scheduled`, and passes `env as unknown as Env` because the test env has no `ASSETS` binding.
- 2026-10-14: A request for an unknown `/api/*` route (the removed `/api/orders/confirm`) built Better Auth in the app-wide middleware, whose background schema check outlived the reply and aborted the pool ("Isolated storage failed", exit 1, test counted as not run). Better Auth is now built only on `/api/auth/*` and inside `requireSession`; `await auth.$context` did not help. `event.data.object` needed `as Stripe.Checkout.Session` to read `client_reference_id`.
- 2026-10-14: Design lesson (final review): the order must be built from what Stripe charged (the snapshot in the session's metadata and `amount_total`), not from the cart when the webhook arrives; the plan's Task 5 read the cart at delivery time, so a cart changed or emptied after payment gave the wrong order.
- 2026-10-14: Narrowing `event.type` to the two checkout events types `event.data.object` as `Stripe.Checkout.Session` once `event` is typed `Stripe.Event`, so the cast is gone. `stripe trigger` sends sessions with no `client_reference_id`, so the webhook answers 200 and logs `webhook_ignored` rather than 400, which Stripe would retry for days.
- 2026-10-14: a GitHub Actions expression inside a YAML flow mapping, `concurrency: { group: ${{ github.ref }} }`, is not valid YAML (`${{` opens a nested flow mapping; js-yaml: "missed comma between flow collection entries"). The plan's Task 20 workflow had it twice; both are block style now. Flow style stays fine for plain values like `with: { node-version: 22 }`.
- 2026-10-14: the live e2e run (Task 19 Step 4). Stripe's hosted Checkout page lists the payment methods as an accordion (Card, Cash App Pay, Klarna) and renders the card inputs only once Card is chosen; the chooser is `[data-testid=card-accordion-item-button]`, which has no clickable box of its own (a pointer click is intercepted by a cover element, and a forced click reports "outside of the viewport"), so the test dispatches the click event. The card form has `#cardNumber`, `#cardExpiry`, `#cardCvc`, `#billingName`, `#billingPostalCode` (ZIP, required for a US card), a "Save my info" checkbox `#enableStripePass` (Link; it asks for a phone number when on) and the submit `[data-testid=hosted-payment-submit-button]`. Email is `#email` and is empty until filled (`customer_email` was not set on the session).
- 2026-10-14: the Stripe CLI profile must match the key's account. A key from a Stripe Sandbox belongs to the Sandbox's own account id, not the parent account's, and the CLI's default profile may be the parent; a `stripe listen` on the wrong profile sees nothing. `stripe listen --project-name "<profile>"` fixes it; `stripe config --list` shows the profiles.
- 2026-10-14: port 8787 was held by another project's `wrangler dev`, left running for days. The shop ran on 8799 with `wrangler dev --port 8799 --local-upstream localhost:8799 --var BETTER_AUTH_URL:http://localhost:8799 --var SITE_URL:http://localhost:8799` (Better Auth needs its base URL to match the origin), `E2E_URL=http://localhost:8799 pnpm e2e`, and `stripe listen --forward-to localhost:8799/...`.
- 2026-10-14: Node's `fetch` sends `Origin: null` on a POST (the fetch spec's "cors" mode with no document origin) and Better Auth answers 403 "Request blocked: wrong origin"; `curl` with no Origin at all is let through. The smoke script sends `origin: <base>` on every POST.
- 2026-10-14: `stripe trigger checkout.session.completed --add checkout_session:client_reference_id=<id> --add 'checkout_session:metadata[items]=<json>'` sets both fields on the fixture's session (verified: the webhook recorded the order). The fixture's session arrives `payment_status: "paid"`.
- 2026-10-14: a Checkout session whose `client_reference_id` is no user in this database (a `stripe trigger` with a made-up id, or an event meant for another environment) hit the order table's foreign key: 500, and Stripe would retry for days. The webhook now checks the user exists and answers 200 + `webhook_ignored` ("unknown user"). Found by the smoke script's first broken run.
